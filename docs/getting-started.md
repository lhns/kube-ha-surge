# Getting started

This walks through installing ha-surge, opting a workload in, and watching
make-before-break work during a node drain.

## Prerequisites

- A Kubernetes cluster, **v1.25+**.
- `kubectl` and `helm` v3.8+ (for OCI chart support).
- Either **cert-manager** installed in the cluster (default webhook cert
  source), or use `--set webhook.certSource=helm` for a self-signed cert
  generated by the chart.

## 1. Install the operator

### With cert-manager (default)

```sh
helm install ha-surge oci://ghcr.io/lhns/charts/ha-surge \
  -n ha-surge-system --create-namespace
```

The chart renders a selfSigned `Issuer` + `Certificate`; cert-manager mints the
serving cert (Secret `ha-surge-webhook-tls`) and its cainjector fills the
webhook's `caBundle`.

### Without cert-manager (self-signed via Helm)

```sh
helm install ha-surge oci://ghcr.io/lhns/charts/ha-surge \
  -n ha-surge-system --create-namespace \
  --set webhook.certSource=helm
```

The chart generates a self-signed CA + serving cert with Helm's
`genCA`/`genSignedCert`, stores it in the Secret, and injects the CA into the
webhook config's `caBundle`. The cert is reused across `helm upgrade` (via
`lookup`) so it does not rotate on every reconcile.

### Verify

```sh
kubectl -n ha-surge-system get deploy ha-surge-controller
kubectl get validatingwebhookconfiguration ha-surge
```

The Deployment should be `Available` and the webhook registered.

## 2. Opt in a namespace

Enablement rides on one key, `ha-surge.lhns.de/enabled`, resolved most-specific
wins: **Deployment annotation → Namespace label → chart `defaultEnabled`** (which
defaults to `false`). With the default, the webhook only sees evictions in
namespaces you label — the blast-radius gate — so the usual move is to enable a
whole namespace at once:

```sh
kubectl label namespace my-app ha-surge.lhns.de/enabled=true
```

Every single-replica Deployment in `my-app` is now covered — no per-Deployment
annotation needed.

> To cover the whole cluster instead, install with `--set defaultEnabled=true`
> (`kube-system` and the release namespace are always excluded). See the
> [reference](reference.md#opt-in-contract--the-enabled-cascade).

## 3. Override a single Deployment (optional)

Use the same key as an annotation to override the namespace default for one
workload — e.g. opt a noisy Deployment *out* of an otherwise-enabled namespace:

```sh
kubectl annotate deployment noisy -n my-app ha-surge.lhns.de/enabled=false
```

Or in the manifest:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: my-app
  annotations:
    ha-surge.lhns.de/enabled: "true"   # redundant if the namespace is enabled
spec:
  replicas: 1
  # ...
```

> The annotation only *overrides* within a namespace the webhook already sees.
> With `defaultEnabled: false`, annotating a Deployment in an **unlabelled**
> namespace has no effect — label the namespace first (see
> [limitations](limitations.md)).

ha-surge only covers Deployments that are **single-replica**, use a
**RollingUpdate** strategy (not `Recreate`), and whose pods do **not** mount a
`ReadWriteOnce` volume. Anything else is passed through untouched (see
[limitations](limitations.md)).

## 4. Watch it work

Drain the node hosting the pod:

```sh
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
```

In another terminal, watch the detached cover pod:

```sh
kubectl get pods -n my-app -w -l ha-surge.lhns.de/detached=true
```

You'll see:

1. `kubectl drain` issues an eviction; the webhook detaches the doomed pod from
   its ReplicaSet (removes `pod-template-hash`) and replies 429. `drain` prints
   something like `error when evicting pod ... (will retry after 5s): Too Many
   Requests` and keeps retrying.
2. The ReplicaSet, now one pod short, creates its own replacement. Meanwhile the
   detached pod keeps serving (the Service selects it — it still carries the app
   labels, just not `pod-template-hash`).
3. Once the ReplicaSet's replacement is `Ready`, the next retry's eviction is
   allowed; the original (detached) pod is removed.
4. The controller deletes the detached cover pod once the replacement is Ready.

At no point was the workload without a serving pod.

## 5. Uninstall

```sh
helm uninstall ha-surge -n ha-surge-system
```

A pre-delete hook removes any leftover detached cover pods cluster-wide
(`-l ha-surge.lhns.de/detached=true`). It is best-effort and never blocks the
uninstall. To skip it and clean up manually:

```sh
helm uninstall ha-surge -n ha-surge-system --no-hooks
kubectl delete pods -A -l ha-surge.lhns.de/detached=true
```

## Development install (kustomize)

For local dev against the current kubeconfig context, the `config/` kustomize
overlay renders the operator without Helm:

```sh
make deploy      # kubectl apply -k config/default
make undeploy
```

The non-Helm path uses a placeholder webhook `caBundle`; supply a real serving
cert Secret (`ha-surge-webhook-tls`) out of band (e.g. a cert-manager
`Certificate` against the `ha-surge-webhook` Service) for the webhook to be
reachable.
